# App Canvas

Create one navigable overview of real UI code. Keep the canvas engine in the shared `@tombelieber/app-canvas` package; each application owns only its catalog, synthetic fixtures, preview adapter and interaction checks.

For first-time integration, read the public [agent guide](https://github.com/tombelieber/app-canvas/blob/main/AGENT_GUIDE.md) and its complete [React/Vite reference](https://github.com/tombelieber/app-canvas/tree/main/examples/react-vite). The [hosted synthetic StoolSense canvas](https://tombelieber.github.io/app-canvas/) demonstrates the expected overview and interactions. An agent can follow the guide without a vendor-specific skill loader.

## Integrate

1. Read the repository's commands and boundaries. Inspect actual routes, existing full-page stories, providers, styles and test fixtures. Reuse working Storybook previews when present; otherwise render the real app in an isolated preview entry using its existing build pipeline.
2. Use the shared CLI. For reproducible repository commands, add `github:tombelieber/app-canvas#v0.6.0` as a dev dependency with the project's package manager, then run `npx app-canvas browsers`. Optional user skill setup: `npx app-canvas install --target both`. A global CLI installation is also supported. Canonical skill source: `tombelieber/tomstack`, `skills/engineering/app-canvas`; the tool includes an installer compatibility snapshot.
3. Add a project config exporting `title`, `groups`, `catalog`, `flows`, optional `pages` and checked `journeys`, `watchPaths`, and `preview(ctx)`. The preview returns `url(screen)` and optional `build`, `handle`, `close` hooks. `readScenario` from `virtual:app-canvas-preview` retains the synthetic case through ordinary HTML navigation. `ctx.createVitePreview` reuses the application's Vite configuration. Vite and custom HTML served through `handle` receive the shared frame bridge automatically; separate-origin custom servers apply `ctx.bridgeHtml(html)` before app scripts. See the working example before inventing another renderer.
4. Inventory every actual page. Classify redirects and external destinations explicitly. Register meaningful states such as populated, empty, loading, error, denied, forms, dialogs and completion; include viewport and source module. Declare page ownership from the router using `pages: [{ id, title, route? }]` and `pageId`/`feature` on each state. Existing configs fall back to groups; do not invent routes or infer hierarchy from graph hops. Import production components and CSS. Fixtures provide inputs and dependencies, never a second implementation of the screen.
5. Keep the preview disposable and isolated. Inject synthetic identity, data and mutations at existing dependency boundaries. Reject unknown requests; never reuse production sessions, call live providers, publish content, change real permissions or open production databases to make a preview work. Do not weaken the real app's guards.
6. Add a `ui:review` command and run the CLI with `--verify`. Every registered screen appears as full source-rendered HTML/CSS in the overview and graph; do not substitute summary cards. Selection and playback run the original app code. Check the important user interactions, failure recovery, reset/isolation, responsive widths, source-change refresh and absence of remote requests. Flow links and graph edges must select, pan and zoom to their destination, including across filters. Configure `routeCoverage` against the actual router and retain `pattern` on base cases; make omissions explicit and red-capable.
7. Record page/redirect/state counts and omissions in `ui-review/README.md`. Prove the coverage guard fails when a page is removed. Verify real controls perform mutations and recover from errors; a drawn flow edge is not interaction proof. Hand over a working URL, not only setup instructions.

## Maintain

- Existing UI edits should update through the real source and watcher. A new state still needs an explicit case and, where relevant, a flow edge. Do not claim arbitrary code reveals every possible condition automatically.
- Show complete source-rendered UI in both the default overview and state graph, never screenshot thumbnails or metadata cards. The measurement pass captures real HTML/CSS into script-free documents; selection, Interact and playback use the original app. Source rebuilds refresh both. Keep the iPad landscape baseline: one compact toolbar, a left navigation sidebar, and a large canvas. Keep the right sidebar collapsible so users can recover canvas width without changing the layout. Page/feature/depth filters stay in the sidebar. Panels must collapse and recover; Browse locks controls, Interact unlocks the selected app, and flow links reveal/pan/zoom to destinations across filters.
- DOM-compatible content uses four touch / eight desktop running-app slots, including playback. Offscreen passive documents are released. Unsupported drawing, embedded/shadow content, inaccessible styles or legacy manifests retain their actual live renderer; measure those extra frames rather than falsely claiming the regular budget. See the tool's [workbench contract](https://github.com/tombelieber/app-canvas/blob/main/docs/workbench.md). During playback do not boot duplicate compatible fixtures. Retain interacted frames across filters/modes and require explicit release at draft capacity. Keep iframe ancestors in stable DOM order; reset only the chosen case. Both Storage APIs are namespaced in disposable tab storage; adapters must isolate IndexedDB/SDK caches too. These are trusted-code previews.
- Author all reviewed happy/failure/recovery journeys using the tool's [journey contract](https://github.com/tombelieber/app-canvas/blob/main/docs/journeys.md). Playback performs real controls and assertions in one continuing session and follows confirmed states; flow links navigate independently seeded cases. `--verify` executes authored journeys. Wait for distinguishing output or replacement DOM after asynchronous changes; the file action supports `replaces` for an asynchronously replaced form. Retain real pointer/keyboard E2E checks too.
- Give every named state a `kind: "case"` journey with a state-specific DOM assertion and explicit starting condition. Enable `coverage: { requireAllCases: true, requireConnected: true }`; prove a missing case/connection fails. Use `outcome` labels for neutral/success/failure/pending/warning and dashed `condition`/`reference` edges for fixture variants instead of inventing clicks. See the journey contract for the exact schema.
- Hand over both the full-UI overview and full-screen state graph. Verify all-flow/all-case queue playback, fresh data between flows, state retained within a flow, single-step across boundaries, replay, failure stopping and camera follow. Coverage counts mean authored cases; report actual playback results separately.
- Measure the target project. Check landscape first (52px toolbar, large canvas, on-demand docked sidebars and no summary cards), then portrait/split view, touch targets, one-finger pan, pinch zoom, Browse/Interact, panel restore, retained drafts, full-capacity handling and playback. The 77-case demo and WebKit iPad emulation do not prove physical iPad memory limits or arbitrary heavy apps. Source edits reload previews; new states still need registration. Verify that a new static runtime can read the previous public project metadata during a cached upgrade.
- A web preview does not qualify native iOS/Android behavior. Add and verify a simulator/device adapter separately when requested.
- Public hosting requires an explicitly publishable synthetic adapter, publication authority and artifact review. `app-canvas export --config <config> --out <new-directory>` shares the same canvas runtime; `preview.exportStatic` supplies the reviewed frontend. It does not automatically remove private data or make any backend static.
- Report the working canvas URL, registered coverage, exercised interactions and exact limitations. Application release and public demonstration require their own authorization and qualification.
