# App Canvas

Deliver the repository's complete UI landscape in one navigable canvas. The user supplies a repository and a capable coding agent; the agent owns discovery, state enumeration, fixtures, render setup, population and coverage verification. Keep the canvas engine in the shared `@tombelieber/app-canvas` package; each application owns its inventory, catalog, synthetic fixtures, preview adapter and checks.

## Required completion contract

Read [references/completion.md](references/completion.md) before integrating or populating a canvas. Adding App Canvas to an application means complete population by default. A skill/CLI-only installation stays within that requested scope. A pilot, representative subset or a few working screens is an intermediate result; continue through the remaining inventory without asking whether to proceed. Narrow scope only when the user requests it. Missing previews, component isolation and test data are implementation tasks owned by the agent.

Build the source inventory independently of the canvas catalog. Account for all screens, shared UI, variants, states and navigation, including data-driven and platform-specific branches. Map every item to rendered cases and state-specific evidence. Enable the independent UI-delivery and all-case gates at handover; a passing catalog alone is insufficient. Group by actual page → feature → state, with platform/size as variants. Keep the whole-app overview and connected flows usable for a newcomer. A blocked item remains incomplete, visible and counted. Reporting a limitation never converts it to accepted scope.

Follow the [population workflow](references/population.md): run `plan` on the whole original repository, inspect all files and UI anchors, enumerate meaningful states and reconcile them against actual navigation. Use `app-canvas guide` from the installed CLI so the instructions match its capabilities. Final **UI delivery** requires `--ui-complete`; `populate` runs the durable adapter queue and then that fresh gate. The existing `--complete` remains an unchanged, stricter [all-source audit](references/source-audit.md). Keep audit-only work separate from missing UI; never relabel an audit failure as a pass. If both are requested, finish both.

For UIKit/storyboards, SwiftUI, Android Views/XML/Compose, React Native or other device UI, also read [references/native.md](references/native.md). Use the original native renderer and agent-authored harnesses. Full native captures are valid canvas surfaces with source/build provenance; distinguish captured UI from live native interaction. Select this path from the actual framework, without requiring a React rewrite.

For first-time integration, read the [agent guide](https://github.com/tombelieber/app-canvas/blob/main/AGENT_GUIDE.md) matching the installed tool revision. For web/Vite integration also read its [React/Vite reference](https://github.com/tombelieber/app-canvas/tree/main/examples/react-vite). The [hosted synthetic StoolSense canvas](https://tombelieber.github.io/app-canvas/) demonstrates the overview and web interactions. An agent can follow the guide without a vendor-specific skill loader.

## Integrate

1. Read the repository's commands and boundaries. User input is the repository; own ordinary setup and continue without repeated questionnaires or “continue” prompts. Inspect entry points, UI source roots, navigation, resources, metadata and UI-affecting conditions. Produce the independent inventory before choosing renderable cases. Reuse working stories/previews; create missing fixture and harness boundaries using original UI code.
2. Use the shared CLI. Install `github:tombelieber/app-canvas#v0.13.0` with the project's package manager and lockfile, or pin a newer verified tool revision; the UI-delivery commands in this development skill require its qualified commit until released (v0.12.0 predates them). Ensure it exports `@tombelieber/app-canvas/inventory` for the completion gate. Run `npx app-canvas browsers`. Optional user skill setup: `npx app-canvas install --target both`. A global CLI installation is also supported. This skill and its references are canonical at `tombelieber/app-canvas`, `skills/app-canvas`, and ship with the matching CLI release. No separate skill repository is required.
3. Add a project config exporting `title`, `groups`, `catalog`, `flows`, optional `pages` and checked `journeys`, `watchPaths`, and `preview(ctx)`. The preview returns `url(screen)` and optional `build`, `handle`, `close` hooks. `readScenario` from `virtual:app-canvas-preview` retains the synthetic case through ordinary HTML navigation. `ctx.createVitePreview` reuses the application's Vite configuration. Vite and custom HTML served through `handle` receive the shared frame bridge automatically; separate-origin custom servers apply `ctx.bridgeHtml(html)` before app scripts. See the working example before inventing another renderer.
4. Plan and deduplicate exact equivalent capture inputs before running devices. Reuse builds/artifacts only while source, fixture, layout and lifecycle inputs match. Prioritize supported phones and add tablets only for distinct implemented layouts. Keep repeated content IDs auditable without multiplying identical cards or replaying the same flows. Populate every inventoried UI item and its implemented conditions, including populated, empty, loading, error/recovery, denied, forms, dialogs and completion. Include source module and viewport; account for platform, layout and data-driven variants. Declare page ownership from the actual router/native navigation using `pages: [{ id, title, route? }]` and `pageId`/`feature` on each state. Existing configs fall back to groups; do not invent routes or infer hierarchy from graph hops. Fixtures provide inputs and dependencies, never a second implementation of the screen. Shared components can map to containing screens when every distinct variant is visible there.
   Follow UI object lifetimes through first entry, retry and reused controllers. A toolbar or input accessory allocated after the first render may appear only after a later field is regenerated; capture that visible state and its real controls rather than treating allocation or an initial nil binding as coverage.
5. Keep the preview disposable and isolated. Inject synthetic identity, data and mutations at existing dependency boundaries. Reject unknown requests; never reuse production sessions, call live providers, publish content, change real permissions or open production databases to make a preview work. Do not weaken the real app's guards.
6. Add `ui:review` and resumable `population` tasks with explicit device resources, dependency/input fingerprints and artifact receipts. Run `populate` or `--ui-complete` with the independent UI inventory and semantic state/transition evidence from `verifyUi`. Run the separate `--complete` if all-source audit is requested. Keep one project writer/device actor, continue independent work after a blocker, and resume checkpoints instead of rebuilding completed batches. Use `--check` / `--verify` during construction. Use source-rendered DOM for web and provenance-linked full captures or a verified device adapter for native. Check interactions at their actual runtime, failure recovery, reset/isolation, layout variants, source refresh/recapture and network isolation. Configure supported `routeCoverage` too. Prove omitting a state from both inventory and catalog still fails, and source changes invalidate evidence.
7. Record discovered-versus-rendered counts, actual verification results and blockers in `ui-review/README.md`. Inspect every rendered case for the distinguishing condition, correct source, layout and assets. Continue fixing omissions and render failures until complete. Verify app operations separately from canvas controls; a drawn edge is not interaction proof. Hand over a populated working URL and reproducible refresh commands. Follow the completion reference's delivery fields.

## Maintain

- Existing UI edits should update through the real source and watcher. A new state still needs an explicit case and, where relevant, a flow edge. Do not claim arbitrary code reveals every possible condition automatically.
- Show complete real UI in both the default overview and state graph, never metadata-only cards. Web uses source-rendered DOM; native uses full original captures or a verified runtime adapter as specified in the native reference. For DOM, selection, Interact and playback use the original app; source rebuilds refresh both views. Keep the iPad landscape baseline: one compact toolbar, a left navigation sidebar, and a large canvas. Keep the right sidebar collapsible so users can recover canvas width without changing the layout. Page/feature/depth filters stay in the sidebar. Panels must collapse and recover; Browse locks controls, Interact unlocks the selected app, and flow links reveal/pan/zoom to destinations across filters.
- DOM-compatible content uses four touch / eight desktop running-app slots, including playback. Compatible passive DOM shares one viewport-sized opaque sandbox with isolated shadow trees. Reuse those trees through zoom changes; do not create one browsing context per state. Native top-layer and legacy passive documents retain their isolated renderers and are culled during an active pinch. Include repeated maximum zoom checks for the total browsing-context count, physical surface size and single source-DOM load per case; a running-app count alone does not bound passive work. Unsupported drawing, embedded/shadow content, inaccessible styles or legacy manifests retain their actual live renderer; measure those extra frames rather than falsely claiming the regular budget. See the tool's [workbench contract](https://github.com/tombelieber/app-canvas/blob/main/docs/workbench.md). During playback do not boot duplicate compatible fixtures. Retain interacted frames across filters/modes and require explicit release at draft capacity. Keep iframe ancestors in stable DOM order; reset only the chosen case. Both Storage APIs are namespaced in disposable tab storage; adapters must isolate IndexedDB/SDK caches too. These are trusted-code previews.
- A native adapter may explicitly provide a reviewed, digest-bound `nativeOverview` atlas for captured UI, following the package's [native overview contract](https://github.com/tombelieber/app-canvas/blob/main/docs/native-overview.md). Keep original full captures, source provenance and the existing runtime/player/flow behavior. Atlas pixels are a display optimization, never source/state acceptance evidence or a replacement for Web/React DOM. Requalify capture mapping, near-view originals, retained input, playback, clickable flows and failure fallback on the actual app.
- Author all reviewed happy/failure/recovery journeys using the tool's [journey contract](https://github.com/tombelieber/app-canvas/blob/main/docs/journeys.md). Playback performs real controls and assertions in one continuing session and follows confirmed states; flow links navigate independently seeded cases. `--verify` executes authored journeys. Wait for distinguishing output or replacement DOM after asynchronous changes; the file action supports `replaces` for an asynchronously replaced form. Retain real pointer/keyboard E2E checks too.
- Verify the toolbar's **▶ Demo** entry point as a hands-free audience presentation: selected journey/queue, related whole journeys on a browsed page, or all authored demos by default. Check all/page/flow scope selection, visible action cues, captions/progress, a step timeline, active elapsed and approximate remaining time, 0.5×–4× speed, next step, previous/next Demo, pause/resume/replay and exit/Esc. Positioning rebuilds prerequisites from fresh fixtures; skipped demos remain distinct from verified completions. It reuses the continuing app and existing journey definitions; standalone cases stay labeled as conditions, and missing journeys never become guessed clicks. Demo hides editing chrome without changing panel preferences, restores browsing on exit, and stops at the last confirmed state on error. Keep regular Browse/Interact and step-level playback working. See the journey contract for details.
- Give every named state a `kind: "case"` journey with a state-specific DOM assertion and explicit starting condition. Enable `coverage: { requireAllCases: true, requireConnected: true }`; prove a missing case/connection fails. Use `outcome` labels for neutral/success/failure/pending/warning and dashed `condition`/`reference` edges for fixture variants instead of inventing clicks. See the journey contract for the exact schema.
- Hand over both the full-UI overview and full-screen state graph. Verify all-flow/all-case queue playback, fresh data between flows, state retained within a flow, single-step across boundaries, replay, failure stopping and camera follow. Coverage counts mean authored cases; report actual playback results separately.
- Measure the target project. Check landscape first (52px toolbar, large canvas, on-demand docked sidebars and no summary cards), then portrait/split view, touch targets, one-finger pan, pinch zoom, Browse/Interact, panel restore, retained drafts, full-capacity handling and playback. The 77-case demo and WebKit iPad emulation do not prove physical iPad memory limits or arbitrary heavy apps. Source edits reload previews; new states still need registration. Verify that a new static runtime can read the previous public project metadata during a cached upgrade.
- Keep the independent inventory current when UI, navigation, resource or metadata sources change. Reinspect affected conditions before updating fingerprints and cases. A source hash is freshness evidence, not proof that the agent discovered every semantic branch.
- Fresh canonical discovery may recognize a bounded Objective-C data-only method and its concrete callbacks. Such annotations permit a specific non-UI explanation, never automatic review or whole-file exclusion; unknown calls and visible UI remain required. See [the strict source-audit reference](references/source-audit.md) for this model and its limits.
- A web viewer's checks qualify the viewer. Native render evidence and native interaction evidence must come from the original simulator/device runtime, as detailed in the native reference.
- Public hosting requires an explicitly publishable synthetic adapter, publication authority and artifact review. `app-canvas export --config <config> --out <new-directory>` shares the same canvas runtime; `preview.exportStatic` supplies the reviewed frontend. It does not automatically remove private data or make any backend static.
- Report the working canvas URL, registered coverage, exercised interactions and exact limitations. Application release and public demonstration require their own authorization and qualification.
